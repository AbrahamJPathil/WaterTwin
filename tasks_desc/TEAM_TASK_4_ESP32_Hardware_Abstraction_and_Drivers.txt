TEAM TASK 4 — ESP32-S3 HARDWARE ABSTRACTION & DRIVERS (v2)

HARDWARE UPDATE: there is no solenoid valve, no pump, and no dedicated
water-level/float switch in the bought parts. The sampling chamber is a
passive sidecar plumbed into the tank, so it floods and drains on its own.
IValveController and valve_controller.{cpp,h} are dropped entirely. In their
place, this layer owns one new small responsibility: deriving a
`chamber_wet` signal for the rest of the system, since nothing else can see
it directly. The conductivity probe is a TDS module, not a raw EC probe, so
ec_sensor.{cpp,h} is renamed to tds_sensor.{cpp,h}.

---

1. Your responsibility

You are responsible for making the software communicate with physical hardware.

Your biggest rule:

«OTHER PEOPLE SHOULD NOT NEED TO KNOW WHICH GPIO PIN A SENSOR USES.»

The project explicitly requires hardware abstraction so the intelligence layer interacts with interfaces rather than GPIO/ADC implementation details. That now includes `chamber_wet` — nobody above this layer should know it's inferred from a sensor characteristic rather than read from a dedicated level switch.

7. Chamber presence (replaces the valve/actuator interface for sampling)

There is no valve to open or close, so there is no IValveController. Instead
this layer exposes one read-only signal:

class IChamberPresence {
public:
    virtual bool isWet() = 0;
    virtual ~IChamberPresence() {}
};

For the MVP, back this with the TDS and/or turbidity probe's own
characteristics (an analog probe floating in air reads very differently —
noisier, often pinned near zero or near full-scale — than one submerged),
rather than a dedicated sensor. Document exactly which signal and threshold
you used in `chamber_presence.cpp`, since this is a judgment call that Task 2
and Task 3 both depend on.

Open item for the team: if presence detection from TDS/turbidity alone turns
out unreliable in practice, the cheapest fix is a simple two-wire continuity
probe or a small float switch — flag this back to the group rather than
silently degrading `chamber_wet` accuracy.

The only real actuator left is the transducer:

class IUltrasonicController {
public:
    virtual bool startCleaning() = 0;
    virtual bool stopCleaning() = 0;
};

The specification requires actuator interfaces such as this and explicitly says the ESP32 must not directly drive high-current loads. The 60 W transducer needs its own driver board (MOSFET/half-bridge, impedance-matched) — this controller only toggles it on and off.

8. Mock hardware

Before the real hardware arrives, create:

MockPHSensor
MockTDSSensor
MockTurbiditySensor
MockTemperatureSensor
MockChamberPresence
MockUltrasonicController

Example:

SensorReading MockPHSensor::read()
{
    return {
        SensorType::PH,
        timestamp,
        7.2f,
        0.98f,
        ReadingStatus::VALID
    };
}

MockChamberPresence must be able to flip between wet and dry on command from
a test, since Task 1's state machine has to survive the chamber going dry
mid-cycle — that's a real operating condition here, not an edge case.

This allows the rest of the team to test the application now.

10. RTC

Provide:

uint64_t getTimestamp();

Do not let other modules directly talk to the DS3231.

They ask:

clock.now();

The project requires timestamps and persistent event history, and the hardware target includes a DS3231 RTC and microSD.

---

11. Calibration

Every relevant sensor should eventually support:

calibrate()
getCalibrationStatus()
applyCalibration()

Calibration data should be stored separately.

Do NOT bury calibration coefficients inside intelligence/ML code. This is explicitly required by the project specification. This applies to the TDS module's ppm mapping too — don't assume the stock calibration is correct without checking it against a known solution.
